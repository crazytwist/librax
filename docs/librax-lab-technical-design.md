# LibraX 实验室自动化平台 — 技术方案

> 版本：v1.2  
> 日期：2026-07-28  
> 读者：产品、交付实施、研发

---

## 一、产品目标

### 1.1 要解决什么问题

实验室现场需要把 **设备、物料、库位、样本、检测流程** 串成可配置、可执行、可追溯的自动化能力；设备侧产生的数据还要能 **采集、解析、入库到业务结果**，最终支撑报告与溯源。  
交付实施人员负责「配得通、跑得动、采得到、排得了障」；客户侧人员需要「看得见状态、盯得住设备、查得到结果、拿得到报告」，而不必关心流程怎么编排、报文怎么解析。

### 1.2 双端产品定位

| 端 | 目标用户 | 核心目标 | 不做什么 |
|----|----------|----------|----------|
| **后台系统** | 现场交付、实施、运维 | 完成接入、配置、编排、采集映射、试跑、排障与干预 | — |
| **前台系统** | 客户（实验室使用方、管理人员） | 流程状态展示、大屏、设备监控、执行日志、检测结果、报告 | 不编辑流程、不配置采集映射、不深度调试设备、不做复杂运维干预 |

### 1.3 产品成功标准

1. **交付可独立配通**：一条含仪器（及可选 AGV）的检测线，从设备接入到流程发布可闭环。  
2. **执行可靠可追溯**：流程实例状态清晰，节点参数、设备下发、回调可查。  
3. **采集可落到结果**：设备回传数据经采集链路解析后，写入样本结果 / 执行上下文，可供报告使用。  
4. **客户可只读运营**：前台可看状态、监控、日志、结果，并下载报告。  
5. **领域边界清晰**：样本独立于普通资源；流程「定义」与「实例」分离；采集连接「设备原始数据」与「业务结果」；前后台权限分离。

### 1.4 设计原则（支撑目标）

- **领域清晰**：设备 / 资源 / 库位 / 样本 / 流程定义 / 流程实例 / 数据采集 / 报告，边界明确。  
- **前后台分离**：同一后端，`/admin-api` 与 `/app-api` 按角色裁剪。  
- **定义与执行分离**：流程定义可版本化；运行产生独立实例。  
- **采集合结果分离**：设备侧保留原始数据；业务侧落结构化结果；映射规则可配置。  
- **设备可扩展**：普通仪器与 AGV 共用设备底座，差异能力插件化。  
- **样本独立**：样本是被检测对象，不是耗材/物料。  
- **渐进演进**：对齐现有 `device / resource / lab / flow` 模块，按阶段补齐缺口。

## 二、模块功能

### 2.1 模块总览

| 序号 | 模块 | 一句话职责 | 后台 | 前台 |
|------|------|------------|------|------|
| 1 | 设备管理 | 设备接入、命令、监控；含特殊设备 AGV | 配置与调试 | 状态/大屏只读 |
| 2 | 资源管理 | 耗材、物料、试剂主数据与库存 | 维护 | 可选只读 |
| 3 | 库位管理 | 空间区位与存放/点位关系 | 规划配置 | 大屏/位置只读 |
| 4 | 样本管理 | 样本生命周期、与流程绑定、结果与溯源 | 建样与异常处理 | 进度/溯源只读 |
| 5 | 流程定义 | 节点拖拽编排、并行/分支、触发器、节点 field | 编排与发布 | 不暴露 |
| 6 | 流程实例 | 定义的一次执行：参数、下发、回调、运维干预 | 启停/重试/排障 | 状态与业务日志只读 |
| 7 | 数据采集 | 从设备接入采集原始数据，解析映射后写入业务结果 | 映射配置与排障 | 结果只读（不看原始报文） |
| 8 | 流程结果报告 | 执行结果归档为可交付报告 | 模板与归档管理 | 查看/下载 |

### 2.2 模块关系

```text
资源 / 库位 ──────────────┐
设备（含 AGV）──► 数据采集 ─┤
样本 ◄──────────── 结果写入 ┤
                          ├──► 流程定义 ──► 流程实例 ──► 报告
                          │         ▲              │
                          └─────────┘              └──► 触发采集落结果
                    执行时调用设备、绑定样本、读写库位
```

- **流程定义**：描述「怎么跑」。  
- **流程实例**：真正「跑起来」，调用设备、更新样本、写上下文。  
- **数据采集**：承接设备回调/上报的原始数据，按规则解析并写入样本结果、执行上下文等业务结果。  
- **报告**：基于结构化结果生成客户交付物。  
- **前台**不参与定义、采集映射配置与执行控制，只消费状态、监控、日志、结果、报告。

### 2.3 与现有代码映射

| 业务模块 | 现有工程模块 |
|----------|----------------|
| 设备管理 | `librax-module-device` |
| 资源 / 库位 | `librax-module-resource`（Material / Location） |
| 样本管理 | `librax-module-lab`（含 SampleResult） |
| 流程定义 / 实例 | `librax-module-flow`（回调、ExecutionContext） |
| 数据采集 | 待显式化（现散落在设备回调、Codec、流程上下文、样本结果写入） |
| 报告 | 待升格（现有归档/溯源雏形分散在 flow、lab） |
| 账号权限 / 文件 / 任务 | `system` / `infra` / `framework` |

## 三、每个模块明细

### 3.1 设备管理

#### 3.1.1 目标

让现场设备「接得上、叫得动、状态清、回得来」。普通检测仪器与 AGV 共用底座，AGV 在任务/点位上做扩展。

#### 3.1.2 功能清单

| 功能 | 说明 | 后台 | 前台 |
|------|------|------|------|
| 设备接入 | 登记设备主数据：编号、名称、类型、协议、所属区域等 | ✓ | ✕ |
| 编解码配置 | 指令模板、报文编解码（Codec） | ✓ | ✕ |
| 设备命令 | 手工/流程下发命令，记录命令流水 | ✓ | ✕ |
| 设备监控 | 在线状态、心跳、告警、大屏点位 | ✓ | ✓ 只读 |
| 回调接入 | 设备任务完成回调；原始数据交给数据采集模块处理并驱动流程继续 | 系统能力 | — |
| AGV 扩展 | 搬运任务、库位点位、路径相关配置 | ✓ | 状态只读 |

#### 3.1.3 核心对象

| 对象 | 说明 |
|------|------|
| DeviceInfo | 一台物理设备的主数据 |
| DeviceCodec | 命令编解码模板 |
| DeviceCommand | 一次命令下发记录 |
| DeviceGateway | 统一：下发 / 查状态 / 取消 |
| DeviceDriver | 按协议或厂商的驱动实现 |

#### 3.1.4 AGV 特殊说明

```text
设备底座（通用）
  ├── 普通仪器：MEASURE 等 → 结果回调
  └── AGV
        ├── 复用：接入、心跳、命令、回调、监控
        └── 扩展：搬运任务、取放点（关联库位）、路径/冲突策略
```

- 流程中通过 `INSTRUMENT + deviceType=AGV` 下发任务。  
- AGV 专属属性进扩展字段或独立 Profile，避免污染通用设备模型。

#### 3.1.5 关键交互

1. 流程节点或人工调试调用 `DeviceGateway.sendCommand`。  
2. 返回 `taskId`，与流程步骤绑定。  
3. 设备完成后回调，进入 **数据采集**（落原始数据 → 解析映射 → 写业务结果）。  
4. 采集成功后推进流程步骤；超时可取消任务并由流程 Watchdog 处理。

#### 3.1.6 现有锚点

- `device.gateway.DeviceGateway`  
- `DeviceInfo` / `DeviceCommand` / `DeviceCodec` / `DeviceDriver`

### 3.2 资源管理（耗材 / 物料 / 试剂）

#### 3.2.1 目标

管理实验室「可消耗、可配置」的物资主数据；**不包含样本**（样本见 3.4）。

#### 3.2.2 功能清单

| 功能 | 说明 | 后台 | 前台 |
|------|------|------|------|
| 物料主数据 | 编码、名称、类型、类别、状态 | ✓ | 可选只读 |
| 类型区分 | 耗材 / 物料 / 试剂（枚举或类别字段） | ✓ | ✓ |
| 物料配置 | 规格、阈值、业务扩展配置 | ✓ | 可选只读 |
| 库存（建议补齐） | 数量、批次、有效期、预警 | ✓ | 可选只读 |

#### 3.2.3 核心对象

| 对象 | 说明 |
|------|------|
| Material | 物料基础信息 |
| MaterialConfig | 物料业务配置 |
| Inventory（建议） | 库存与批次 |

建议类型：`CONSUMABLE`（耗材）、`MATERIAL`（物料）、`REAGENT`（试剂）。

#### 3.2.4 边界说明

| 属于资源 | 不属于资源 |
|----------|------------|
| 耗材、物料、试剂 | 样本（独立域） |
| 库存与效期 | 设备、流程定义 |

#### 3.2.5 现有锚点

- `resource`：`Material` / `MaterialConfig`

### 3.3 库位管理

#### 3.3.1 目标

描述实验室空间拓扑，支撑存放、设备安装点、AGV 点位、样本当前位置。

#### 3.3.2 功能清单

| 功能 | 说明 | 后台 | 前台 |
|------|------|------|------|
| 区位树 | 区域 → 货架 → 库位等多级结构 | ✓ | 只读展示 |
| 区位属性 | 编码、名称、类型、坐标、用途、状态 | ✓ | ✓ |
| 关联存放 | 与物料库存关联 | ✓ | 可选 |
| 关联设备/AGV | 设备安装点、AGV 停靠/取放点 | ✓ | 大屏点位 |
| 样本位置 | 样本当前库位（流转溯源） | ✓ | ✓ 只读 |

#### 3.3.3 核心对象

| 对象 | 说明 |
|------|------|
| Location | 树形区位；含 parent、level、coordinates、purpose 等 |

#### 3.3.4 关联关系

```text
Location 1 ── * 物料/库存
Location 1 ── * 设备安装点
Location 1 ── * AGV 点位
Sample.当前库位 → Location
```

#### 3.3.5 说明

产品菜单上「库位」独立；工程上可暂挂在 `resource` 模块，不影响前后台职责划分。

#### 3.3.6 现有锚点

- `resource.Location`

### 3.4 样本管理

#### 3.4.1 目标

管理被检测对象的全生命周期：建样、入流程、步骤状态、结果、事件、拆分与溯源。  
样本是业务真相的重要载体，**不能当作普通耗材**。

#### 3.4.2 功能清单

| 功能 | 说明 | 后台 | 前台 |
|------|------|------|------|
| 样本建档 | 登记样本主数据 | ✓ | ✕（或仅扫码登记若产品需要） |
| 流程绑定 | 样本进入某次流程实例 | ✓ | 进度只读 |
| 步骤状态 | 样本在各检测步骤上的状态 | ✓ | ✓ |
| 结果记录 | 检测结果落库（可由数据采集写入） | ✓ | 结果查看 |
| 事件与溯源 | 生命周期事件、追溯报告 | ✓ | ✓ 只读 |
| 样本拆分 | 父子样本关系（对应流程 SAMPLE_SPLIT） | ✓ | 关系只读 |
| 异常处理 | 失败标记、人工处理 | ✓ | ✕ |

#### 3.4.3 核心对象

| 对象 | 说明 |
|------|------|
| SampleInfo | 样本主数据 |
| SampleStep | 样本与流程步骤的绑定及状态 |
| SampleResult | 检测结果 |
| SampleEvent | 生命周期事件 |
| SampleRelation | 父子/拆分关系 |

#### 3.4.4 与流程协作

```text
流程实例启动
  → SampleFlowIntegrationListener
  → 样本进入流程 / 步骤开始结束更新 / 成功失败标记
```

约定：样本域异常降级记日志，默认不阻断流程引擎（可按项目调整）。

#### 3.4.5 现有锚点

- `lab`：Sample* 服务与 `SampleFlowIntegrationListener`

### 3.5 流程定义

#### 3.5.1 目标

供交付实施人员可视化编排检测流水线：节点、依赖、分支、触发器、节点 field，校验后发布。

#### 3.5.2 功能清单

| 功能 | 说明 | 后台 | 前台 |
|------|------|------|------|
| 流程定义 CRUD | 名称、版本、启停、补偿策略等 | ✓ | ✕ |
| 节点拖拽编排 | 画布拖拽、连线表达依赖 | ✓ | ✕ |
| 节点类型配置 | 仪器/计算/条件/等待/通知/样本拆分等 | ✓ | ✕ |
| 并行 | 多节点依赖满足后并行调度 | ✓ | ✕ |
| 分支（网关语义） | 条件节点 + 多分支配置 | ✓ | ✕ |
| 触发器 | 手工、定时、事件、外部 API 等 | ✓ | ✕ |
| 节点 field | 输入输出字段、映射、设备参数模板 | ✓ | ✕ |
| 图校验与试跑 | 发布前校验；Standalone 试跑 | ✓ | ✕ |

#### 3.5.3 核心对象

| 对象 | 说明 |
|------|------|
| PipelineDefinition | 流程定义主数据 |
| StepDefinition / PipelineStep | 步骤模板与流程内节点 |
| PipelineTrigger | 触发器 |
| 节点 field 配置 | 参数与映射（含设备下发模板） |

#### 3.5.4 节点类型

| 类型 | 含义 |
|------|------|
| INSTRUMENT | 仪器 / AGV 异步执行，等待回调 |
| COMPUTE | 本地计算（Bean / LiteFlow） |
| CONDITION | 条件分支（表达式） |
| WAIT | 等待时长或外部信号 |
| NOTIFY | 通知 |
| SAMPLE_SPLIT | 样本拆分 |

#### 3.5.5 并行与分支（实现约定）

| 产品说法 | 技术实现 |
|----------|----------|
| 并行 | DAG：`dependsOn` 全部成功/跳过后，就绪节点并行调度 |
| 分支 | `CONDITION` + 真假分支或多分支；未选中分支标记 SKIPPED |
| 网关 | 一期不单独做 BPMN Gateway 节点；编辑器用「依赖边 + 条件节点」表达 |

#### 3.5.6 现有锚点

- `flow` 定义侧：PipelineDefinition / StepDefinition / PipelineTrigger  
- `PipelineGraphValidator`、`PipelineGraphBuilder`

### 3.6 流程实例

#### 3.6.1 目标

把流程定义跑成一次可观测、可干预的执行：节点参数、设备下发、回调推进、失败重试与日志。

#### 3.6.2 功能清单

| 功能 | 说明 | 后台 | 前台 |
|------|------|------|------|
| 实例启动 | 触发器或手工启动 | ✓ | 默认 ✕（若需「一键开跑」单独授权） |
| 实例状态 | 运行中/成功/失败/取消/超时等 | ✓ | ✓ 只读 |
| 节点执行 | 每个节点状态、耗时、结果 | ✓ | ✓ 业务视角 |
| 执行参数 | 节点实际入参、上下文变量 | ✓ | 脱敏后可选 |
| 设备下发参数 | 真实下发 payload，便于排障 | ✓ | ✕ |
| 回调处理 | 设备/步骤回调推进调度 | 系统 | — |
| 事件日志 | 执行事件流水 | ✓ 含技术明细 | ✓ 业务日志 |
| 运维干预 | 暂停、恢复、终止、单步重试 | ✓ | ✕ |

#### 3.6.3 核心对象

| 对象 | 说明 |
|------|------|
| PipelineExecution | 流程实例 |
| StepExecution | 节点执行记录与状态机 |
| ExecutionContext | 运行时上下文 |
| ExecutionEventLog | 事件日志 |
| 回调记录 | 与 executionId / nodeId / taskId 关联 |

#### 3.6.4 执行链路

```text
Trigger / 手工启动
  → 创建 PipelineExecution + StepExecution
  → DagScheduler 调度就绪节点
  → StepExecutor（Instrument / Compute / Condition / …）
  → Instrument：DeviceGateway.sendCommand
  → 设备回调 → 数据采集（原始数据 → 解析 → 写结果/上下文）
  → 步骤推进 → 再调度
  → 结束；超时由 Watchdog；异常可 Recovery
```

#### 3.6.5 状态（概念）

- 实例：`PENDING → RUNNING → SUCCESS | FAILED | CANCELLED | TIMEOUT`  
- 节点：`PENDING → RUNNING → WAITING → SUCCESS | FAILED | SKIPPED | DEAD`

#### 3.6.6 现有锚点

- `DagScheduler`、`StepExecutor*`、`StepCallback`  
- PipelineExecution / StepExecution / ExecutionContext / ExecutionEventLog

### 3.7 数据采集

#### 3.7.1 目标

把设备接入侧产生的数据（主动上报或命令回调）可靠采集下来，经解析与字段映射后，写入 **样本结果、流程执行上下文** 等业务结果，供后续计算节点、报告与前台结果展示使用。  
定位：连接「设备原始世界」与「业务结果世界」，而不是替代设备管理或样本管理。

#### 3.7.2 功能清单

| 功能 | 说明 | 后台 | 前台 |
|------|------|------|------|
| 原始数据采集 | 接收设备回调/上报报文，持久化原始数据（含关联 execution/device/task） | ✓ 可查可排障 | ✕（不暴露原始报文） |
| 采集通道 | 按设备类型/协议配置接入方式（HTTP 回调、MQ、轮询拉取等） | ✓ | ✕ |
| 解析与解码 | 复用或关联 DeviceCodec，将原始报文转为结构化字段 | ✓ | ✕ |
| 字段映射 | 设备字段 → 样本结果项 / 上下文变量 / 报告指标 的映射规则 | ✓ | ✕ |
| 结果写入 | 写入 SampleResult、ExecutionContext 等；支持覆盖/追加策略 | ✓ | 看结构化结果 |
| 质控与校验 | 必填校验、范围校验、单位换算、异常标记 | ✓ | 异常结果可见 |
| 采集流水 | 每次采集的成功/失败、耗时、错误原因可追溯 | ✓ | 可选业务摘要 |
| 补采/重放 | 对失败或需重算的原始数据重新解析落库（不重复调设备时可仅重放） | ✓ | ✕ |

#### 3.7.3 核心对象

| 对象 | 说明 |
|------|------|
| CollectChannel（建议） | 采集通道：设备类型、协议、接入地址/主题等 |
| CollectMapping（建议） | 字段映射规则：源字段、目标（结果项/上下文 key）、转换表达式 |
| RawCollectRecord（建议） | 原始采集记录：报文、设备、任务、流程步骤关联、采集时间 |
| ParsedResult（建议） | 解析后的结构化结果快照（写入业务前可审计） |
| SampleResult / ExecutionContext | 现有业务结果落点（采集模块的「写出」目标） |

#### 3.7.4 采集链路

```text
设备回传 / 上报
  → 接入校验（签名、token、设备身份）
  → 落 RawCollectRecord（原始数据落库，先存后解析）
  → Codec / 解析器 → 结构化字段
  → CollectMapping 映射 + 质控校验
  → 写入业务结果
        ├── SampleResult（样本检测结果）
        ├── ExecutionContext（供后续 CONDITION / COMPUTE 使用）
        └── （可选）实时推送到前台结果视图
  → 通知流程实例：步骤成功/失败（与 StepCallback 衔接）
```

#### 3.7.5 与相邻模块边界

| 模块 | 数据采集与之关系 |
|------|------------------|
| 设备管理 | 设备负责接入与命令；采集消费设备回调/上报，复用 Codec，不负责设备主数据 |
| 流程实例 | 采集常在 INSTRUMENT 回调时触发；解析成功后再推进步骤；上下文变量由采集写入 |
| 样本管理 | 采集写入 SampleResult；样本生命周期仍由 lab 域管理 |
| 报告 | 报告读取结构化结果，不直接解析设备原始报文 |
| 前台 | 只展示映射后的业务结果与采集状态摘要，不开放原始报文与映射配置 |

#### 3.7.6 关键原则

1. **先存原始、再解析**：原始报文不可丢，便于补采与排障。  
2. **幂等**：同一 `taskId` / 回调重复投递不重复污染业务结果（可按策略覆盖或忽略）。  
3. **映射可配置**：换设备型号尽量改映射，不改流程代码。  
4. **失败可观测**：解析失败保留原始数据 + 错误原因，支持后台重放。

#### 3.7.7 现有锚点与演进

- 现有能力分散在：设备回调、`DeviceCodec`、流程 `StepCallback` / `ExecutionContext`、`SampleResult` 写入。  
- 建议产品与工程上 **显式化数据采集模块**（可先落在 device/flow 协作层，再视复杂度独立包），统一「原始记录 + 映射 + 落结果」闭环。

### 3.8 流程结果报告

#### 3.8.1 目标

把一次（或一批）流程执行结果沉淀为客户可查看、可下载的报告；后台可配置模板与归档规则。

#### 3.8.2 功能清单

| 功能 | 说明 | 后台 | 前台 |
|------|------|------|------|
| 报告模板 | 按流程/检测类型配置模板 | ✓ | ✕ |
| 自动生成 | 流程成功后自动生成 | ✓ | — |
| 手工重生成 | 排障或模板变更后重出 | ✓ | ✕ |
| 报告查看/下载 | 预览、下载、分享 | ✓ | ✓ |
| 归档存储 | 对象存储归档 | ✓ | 通过下载访问 |

#### 3.8.3 核心对象（建议升格）

| 对象 | 说明 |
|------|------|
| ReportTemplate | 报告模板 |
| ReportInstance | 某次执行生成的报告 |
| ReportArchive | 归档文件元数据 |

数据来源：数据采集写入的结构化结果、ExecutionContext、SampleResult、设备结果摘要等。

#### 3.8.4 现状与演进

当前仅有归档/溯源雏形（如报告归档 Bean、样本溯源报告），建议在产品与工程上 **升格为独立报告能力**，以支撑客户前台验收。

## 附录：推荐实施顺序（简述）

1. **夯实后台闭环**：设备 + 库位/资源 + 样本 + 流程定义/实例运维页打通。  
2. **数据采集闭环**：原始落库 + 映射配置 + 写入 SampleResult/Context + 失败重放。  
3. **客户前台 MVP**：状态、大屏、业务日志、结果查看、报告下载。  
4. **AGV 与仓储深化**：任务模型、点位、库存批次效期。  
5. **体验增强（可选）**：报告设计器、AI 辅助排障等。
