项目概述与目标

1.1 系统定位

Librax 是一个面向实验室自动化场景的企业级综合管理平台，融合了 流程编排引擎、设备通信层、样本全生命周期管理、资源调度 和 任务执行框架 五大核心能力，旨在解决现代实验室中流程复杂、设备异构、数据割裂、人工依赖度高等核心痛点。

核心业务场景
  • 样本从签收 → 处理 → 检测 → 归档全流程数字化
  • 多类型仪器（pH 计、浊度仪、分析仪）统一接入与调度
  • AGV 自动搬运与存储架位置精确管理
  • 检测流程 DAG 编排，支持并行、条件分支、失败补偿
  • 样本衍生追溯（原始/分裂/合并/取液）完整谱系
  • 多区域资源共享配额与独占资源管理
设计目标
  • 流程定义与执行分离，支持版本化管理
  • 步骤组件可复用，支持单步独立调试
  • 设备协议插件化（TCP/HTTP/串口/SDK/Mock）
  • 资源独占与共享两种模式，分布式锁保证一致性
  • 全链路可观测：执行日志、事件追踪、关键路径分析
  • 多租户 SaaS 模式，数据隔离，权限精细控制

流程引擎模块 (librax-module-flow)

3.1 模块职责

流程引擎是 Librax 的核心，负责实验检测流程的 定义、版本管理、调度执行、状态追踪、失败补偿 全生命周期管理。基于 DAG（有向无环图）模型，支持步骤并行执行、条件分支、子流程嵌套和单步独立调试。

3.2 流水线执行状态机

PENDING → RUNNING → PAUSED ↔ RUNNING → SUCCESS
RUNNING → FAILED → COMPENSATING → COMPENSATED
RUNNING → CANCELLED

3.3 步骤类型设计

🔬

INSTRUMENT

调用物理仪器，创建 Task 并等待设备回调，异步完成

⚙️

COMPUTE

执行 Spring Bean 方法或 LiteFlow 规则链，同步返回结果

🔀

CONDITION

使用 Aviator 表达式求值，根据结果选择后续分支路径

⏳

WAIT

等待定时器超时或外部信号（DEVICE_CALLBACK / EXTERNAL_EVENT）

🔔

NOTIFY

发送通知（短信/邮件/Webhook），不阻塞后续步骤

🧬

SAMPLE_SPLIT

样本分裂，创建子样本并为每个子样本启动独立分支执行

👤

MANUAL

暂停等待人工审批，支持指定审批人和截止时间

🚀

UNIT_LAUNCHER

启动子流程（子 PipelineExecution），支持嵌套工作流

3.4 DAG 调度引擎设计

DagScheduler 核心逻辑
  1. 从 PipelineStepDO 构建有向图（节点=stepKey，边=precedingNodeIds）
  2. 使用 JGraphT 拓扑排序验证无环性，输出执行序列
  3. 遍历就绪节点（前驱全部 SUCCESS/SKIPPED），并行提交至线程池
  4. 每个节点由 StepExecutorFactory 按 stepType 选择对应执行器
  5. 执行完成后更新 StepExecutionDO 状态，触发下游节点就绪检查
  6. 所有节点完成后，用 JGraphT 计算 关键路径，写入 PipelineExecutionDO.criticalPath

3.5 执行上下文（Context）设计

流水线执行期间，步骤间数据通过 ExecutionContextDO 共享，遵循以下命名空间规则：

命名空间表达式示例来源
input${input.sampleType}流水线启动时传入的参数
ctx${ctx.batchNo}步骤写入的上下文变量
output.{stepKey}${output.ph_measure.value}某步骤的输出字段（由 outputFields 定义）

3.6 失败补偿策略

补偿策略类型
  • NONE：失败后不执行补偿，直接标记失败
  • ON_FAIL：仅在步骤失败时触发补偿步骤
  • ALWAYS：无论成功失败，执行结束后均触发补偿
补偿执行机制
  • 按逆拓扑顺序依次执行已完成步骤的 compensateStepKey
  • 补偿步骤以 runMode=COMPENSATE 标识
  • 创建新的 StepExecutionDO 记录补偿过程
  • 补偿失败记录为 DEAD，人工干预

3.7 单步独立调试

系统支持对任意已标记 runnableStandalone=true 的步骤进行独立执行，用于开发验证和问题排查，无需启动完整流水线：

调用 createStandaloneExecution
→
创建独立 PipelineExecution
(triggerType=STANDALONE)
→
单节点 DAG 调度
→
WebSocket 推送实时状态
→
返回步骤输出结果
Mock 模式：当设备未接入时，使用 StepDefinitionDO.mockOutput 模拟仪器返回数据，使调试不依赖物理设备。

资源调度模块 (librax-module-resource)

6.1 资源所有权模型

独占资源 (EXCLUSIVE)
  • 绑定到特定区域（zoneCode），只能被该区域内的流程使用
  • 例：ZONE-A 的 pH 计，不可被 ZONE-B 借用
  • 无需配额限制，区域内自行管理并发
  • 适合精密仪器、区域固定设备
共享资源 (SHARED)
  • 跨区域共享，任意区域可申请使用
  • 通过 ZoneQuotaDO 限制每个区域的最大借用数
  • 例：AGV 小车，多个区域均可调度，但每区域最多 2 辆
  • Redis 分布式锁保证原子性分配

6.2 资源分配算法

资源分配策略（ResourceAllocationService）:
1. 查询步骤资源需求 (StepResourceReqDO)
2. 优先查找同区域内的可用独占资源
3. 独占资源不足时，检查共享资源配额
4. 使用 Redisson 分布式锁（REDLOCK）原子性执行：
   a. 检查 ZoneQuotaDO.maxBorrow - 当前占用 > 0
   b. 创建 StepResourceHoldDO 记录分配关系
   c. 更新 ResourceConfigDO.currentUsage
5. 资源不足时：任务进入等待队列，持续轮询
6. 步骤完成后：释放持有，通知等待队列重新分配

7.1 任务状态机

PENDING → ASSIGNED → EXECUTING → DONE
EXECUTING → FAILED → （重试次数未耗尽时自动重新 PENDING）
CANCELLED | TIMEOUT 终态，不可恢复

7.2 任务类型与执行器

任务类型执行器类型执行方式回调
INSTRUMENTDEVICEDeviceConnector 发送仪器指令异步（WEBHOOK/POLL）
AGVAGV调度 AGV 搬运（fromLocation→toLocation）异步回调
COMPUTEBEANSpring Bean 方法同步执行同步返回
MANUALHUMAN人工操作，等待人员确认完成手动回调 API
NOTIFYBEAN发送通知（SMS/Email/Webhook）同步返回

7.3 回调验证协议

// 外部系统回调接口
POST /flow/step-callback/{executionId}/{nodeId}

Request Body:
{
  "callbackToken": "a3f9b2c1...",   // 与 StepExecutionDO.callbackToken 比对
  "result": {
    "status": "SUCCESS",
    "output": { "value": 7.2, "unit": "pH" },
    "errorCode": null,
    "errorMsg": null
  }
}

验证逻辑:
1. 查询 StepExecutionDO（executionId + nodeId + status=RUNNING）
2. 比对 callbackToken（防重放攻击）
3. 幂等检查（相同 token 重复回调合并处理）
4. 更新 StepExecution 状态，触发 DAG 调度器继续

7.4 任务优先级与重试

优先级队列
  • CRITICAL (2)：紧急检测，最高优先级，插队执行
  • URGENT (1)：加急检测，优先于普通任务
  • NORMAL (0)：常规检测，按序执行
重试配置
  • retryCount：当前已重试次数
  • maxRetry：最大允许重试次数
  • defaultBackoffMs：重试退避间隔（指数递增）
  • 达到 maxRetry 后标记 FAILED，触发补偿逻辑

9.3 关键设计决策

乐观锁设计：PipelineExecutionDO 使用 row_version（整型版本号）实现乐观并发控制，状态更新时携带期望版本号：
UPDATE pe_pipeline_execution SET status=?, row_version=row_version+1 WHERE id=? AND row_version=?
防止高并发下状态写入冲突（如同时触发暂停和完成）。
每次重试独立记录：StepExecutionDO.attempt 字段标识重试次数，每次重试创建新行，保留完整的执行历史，不覆盖前次失败记录，便于问题回溯分析。

9.4 主要表结构概览

表名中文名记录特征估算量级

pd_step_definition步骤定义可复用组件，低频写千级
pd_pipeline_step流水线步骤关系每条流水线 N 条节点记录万级
pe_pipeline_execution流水线执行实例每次触发一条，高频写百万级
pe_step_execution步骤执行记录每实例 N 步×重试次数千万级
pe_execution_context执行上下文每实例一条，频繁更新百万级
pe_execution_event_log执行事件日志仅追加，全量审计亿级（需归档）

9.5 索引设计原则

  • 所有外键字段（executionId, stepKey, sampleId）建立普通索引
  • 状态字段（status）+ 时间字段（createTime）建立联合索引，支持待处理任务扫描
  • callbackToken 建立唯一索引，防止回调重复处理
  • 事件日志表按月分表，历史数据定期归档至冷存储
  • 执行上下文按 executionId 分区，提升并发查询效率

WebSocket 实时通信设计

11.1 设计目的

流水线执行过程中，前端界面需要实时展示每个步骤的执行进度、状态变化和输出结果，通过 WebSocket（STOMP 协议）实现服务端主动推送，避免频繁轮询。

11.2 推送事件类型

事件类型触发时机推送内容
EXECUTION_STARTED流水线开始执行executionId、pipelineKey、触发人
STEP_QUEUED步骤进入就绪队列nodeId、stepKey、预计执行时间
STEP_STARTED步骤开始执行nodeId、执行设备、inputSnapshot
STEP_SUCCESS步骤执行成功nodeId、outputData、executeMs
STEP_FAILED步骤执行失败nodeId、errorCode、errorMsg、attempt
STEP_RETRYING步骤开始重试nodeId、retryCount、backoffMs
EXECUTION_SUCCESS流水线整体成功totalMs、criticalPath
EXECUTION_FAILED流水线失败failedNodeId、errorMsg
COMPENSATING开始执行补偿compensatingNodes 列表

11.3 订阅地址规范

ws://host:48080/ws  (STOMP over WebSocket)

// 订阅特定执行实例的事件

// 订阅当前用户的全局通知
SUBSCRIBE /user/queue/notify

// 心跳配置
heartbeat: [10000, 10000]  // 10s 心跳保持连接

安全架构设计

认证机制
  • JWT Token 无状态认证（RS256 签名）
  • AccessToken（30分钟）+ RefreshToken（7天）双 Token 机制
  • Token 存储于 Redis，支持强制下线（黑名单）
  • 支持社交登录（JustAuth：微信、钉钉、企业微信）
  • 登录日志记录（IP、设备、成功/失败）
授权机制
  • @PreAuthorize("hasAuthority('flow:execution:create')") 接口级鉴权
  • 部门数据权限过滤（MY/DEPT/DEPT_TREE/ALL）
  • 租户数据隔离（tenant_id 强制过滤）
  • 敏感操作双因素验证（可选）
防护机制
  • 接口限流（基于 Redis 令牌桶，@RateLimiter）
  • 幂等校验（@Idempotent，Redis 去重，防重复提交）
  • 回调 Token 验证（防止伪造设备回调）
  • SQL 注入防护（MyBatis 参数化查询）
  • XSS 防护（输入过滤 + 输出转义）
审计追踪
  • 操作日志（OperateLogDO）：记录所有写操作及操作人
  • 登录日志（LoginLogDO）：认证记录，含失败原因
  • 执行事件日志（ExecutionEventLog）：完整流程追踪
  • 任务事件（TaskEventDO）：任务生命周期记录

性能与可靠性设计

13.1 缓存策略

缓存对象缓存层TTL更新策略
流水线定义Caffeine（本地）10分钟版本变更时主动失效
步骤定义Caffeine（本地）10分钟写入时主动失效
用户权限信息Redis30分钟登出/角色变更时失效
租户配置Redis60分钟配置更新时失效
设备状态Redis心跳周期×2心跳更新
执行上下文DB（主要）+ Redis（热数据）执行期间步骤完成时写 DB

13.2 数据库优化

  • Dynamic Datasource：写操作走主库，读操作走从库（读写分离）
  • Druid 连接池：最大连接数 100，连接有效性检测，慢 SQL 监控
  • MyBatis Plus 分页插件：自动 COUNT 优化，避免全表扫描
  • 高频更新表（StepExecution、Task）：乐观锁替代悲观锁，减少锁竞争
  • 事件日志表：定期归档（按月分表或迁移至 ClickHouse）

13.3 并发控制

分布式锁使用场景
  • 资源分配（ResourceAcquireService）：防止超额分配
  • 流水线状态转换：防止并发状态写冲突
  • 设备并发限制：maxConcurrent 控制并行指令数
  • 任务分配：防止同一任务被多个执行器认领
可靠性保障
  • Quartz 集群模式：Job 调度高可用，防止单点故障
  • MQ 消息持久化：设备任务消息不丢失
  • 死信队列处理：无法消费的消息人工干预
  • 心跳超时检测：自动发现离线设备，告警通知
  • 幂等执行：相同 callbackToken 多次回调安全合并
