01

系统定位与核心思想

Librax 是一套面向实验室自动化场景的 流程编排与执行引擎。它解决的核心问题是：将一组有依赖关系的实验步骤（仪器操作、AGV 搬运、数据计算、条件判断）按 DAG 拓扑顺序并行调度执行，同时保证状态一致性、资源不超卖、故障可恢复。

与通用流程引擎（Temporal、Airflow）的本质区别在于 物理资源维度：每个步骤执行前必须抢占到真实的物理设备（离心机、AGV、显微镜），设备有区域归属和并发限制，这是实验室场景独有的约束。

核心设计哲学

调度器只负责「往前走」——找就绪节点、并行提交。资源申请是「门卫」——步骤执行前必须过的关。异常处理是「擦屁股员」——完全独立于主流程。三者通过事件解耦，各司其职。

DAG 调度

纯拓扑计算，不感知业务。依赖满足即并行提交，靠乐观锁防重复执行。

资源调度

步骤级门卫，Redis 锁 + 区域配额。申请失败不报错，等待重新调度。

异常处理

独立 ExceptionEngine，处理链模式。超时、重试、补偿、告警各司其职。

03

原始设计详解

原始引擎围绕 DAG 调度 + 状态机 + SPI 分发 三核心构建，已实现完整的执行生命周期管理，包括异常处理链、超时扫描、补偿机制。以下是各核心模块的设计原因。

PipelineGraphCache — 懒加载 + 版本隔离
engine/definition/PipelineGraphCache.java

为什么：流程定义是只读的，同一个版本不需要反复解析。运行中的执行实例必须绑定启动时的图版本，不能被后续修改影响。


手段：ConcurrentHashMap<(key,version), Graph>，首次访问时从 DB 加载并缓存，不同版本独立存储。

DagScheduler — 纯拓扑调度
engine/execution/scheduler/DagScheduler.java

为什么：调度逻辑和业务逻辑解耦，才能独立演进。调度器只知道「谁依赖谁」，不知道「步骤做什么」。


手段：每轮 doSchedule() 扫描全部节点状态，找出 PENDING 且依赖全部 SUCCESS/SKIPPED 的节点，并行提交。事件驱动循环推进，无外部定时器。

StepStateMachine — 乐观锁 tryStart
engine/execution/statemachine/StepStateMachine.java

为什么：同一个步骤可能被多次提交（重试、并发调度）。tryStart 用 CAS 保证只有一个线程能成功将步骤 PENDING→RUNNING，其余线程发现失败后自动放弃。


手段：UPDATE ... WHERE status='PENDING' AND version=#{v}，affectedRows=0 则放弃。

ExceptionCoordinator — 处理链
engine/execution/exception/ExceptionCoordinator.java

为什么：超时、重试、补偿、告警是不同的关注点，不能全塞进 onStepComplete。处理链让策略可配置，新增策略无需修改核心代码。


手段：责任链模式，RetryHandler → CompensationHandler → AlertHandler，每个 Handler 处理后返回 HANDLED 或 PASS_TO_NEXT。

ExecutionContextManager — Redis热写+DB冷备
engine/execution/context/ExecutionContextManager.java

为什么：步骤间传递数据（上游输出→下游输入）读写极频繁，DB 响应太慢。同时需要持久化应对 Redis 故障和宕机恢复。


手段：节点输出实时写 Redis，异步写 pe_execution_context 表（JSON 全量覆盖）。恢复时从 DB 重建上下文。

DispatchSpi — 双轨分发
api/dispatch/DispatchSpi.java（接口）

为什么：同步仪器指令（DIRECT）和异步任务队列（QUEUED）的执行模型完全不同，统一接口屏蔽差异，调度器无需感知。


手段：pd_pipeline_step.dispatch_mode 决定使用哪个 SPI 实现，StepSubmitter 通过 DispatchSpiFactory 路由。

原始设计的资源问题

原始设计中 ResourcePool 已有接口定义，但接入点和数据模型存在几个关键问题，本次重构主要解决这些问题。

问题 原始设计 问题所在 本次修复
区域归属 PipelineGraph.zoneCode
（从 pe_pipeline_execution 查）		 区域是步骤级概念，同一流程不同步骤可能在不同区。流程级 zoneCode 语义错误。 删 pe_pipeline_execution.zone_code。pd_pipeline_step 加 zone_code，StepNode 携带，从 node 取。
资源开关 needsResource() 判断
node.deviceType != null		 deviceType 是执行器路由用的，不是资源调度开关。同类步骤不一定都需要抢占资源。 pd_pipeline_step 加 resource_enabled 字段，显式开关，粒度在步骤级。
资源绑定粒度 资源需求没有定义层，无法配置一步多资源 实际业务中一个步骤需要多台设备（如离心机+操作台），无法表达。 新建 pd_step_resource_req，1:N 关联步骤，每行一个资源需求。
释放时机 仅 dispatch 异常时释放，tryStart 失败时释放 步骤成功/DEAD/超时时资源不释放，导致资源永久泄漏。 StepSuccessHandler、StepFailureHandler、TimeoutWatchdog 各加 releaseIfHeld()。
宕机恢复 RecoveryScanner 无资源感知 宕机前已申请资源的步骤，恢复后 Redis 锁还在，导致资源永久锁定。 pe_step_execution 加 resource_acquired 字段，RecoveryScanner 扫到时先释放资源再重置步骤。
审计追踪 只有 Redis 锁记录 Redis 无持久化保证，无法追溯"这个步骤用了哪台设备多少时间"。 新建 pe_step_resource_hold 表，写 DB 记录，released_at IS NULL 表示持有中。

资源调度核心思想

① 资源属于步骤，不属于流程

申请和释放的生命周期跟随步骤执行，不跟随流程。同一流程不同步骤用完全不同的设备。

② 申请必须原子

一步多资源时，要么全部申请成功才执行，要么一个都不占。部分申请会导致资源白白锁住（死锁前置条件）。

③ 资源分三类，策略不同

EXCLUSIVE 固定设备（本区独占）、SHARED 移动设备（全局 + 配额）、SLOT 容量（计数器）。不同类型锁机制不同。

④ 不足时等待，不报失败

资源不足不改步骤状态、不消耗重试次数，直接返回。等资源释放后 DagScheduler 重新触发，步骤再次竞争。

⑤ 防死锁：固定申请序

所有步骤按 sort_order 全局统一顺序申请资源。步骤A和步骤B都按 CENTRIFUGE→AGV 顺序申请，死锁从根本消除。

⑥ 资源泄漏三道防线

正常：StepSuccessHandler/FailureHandler 释放。超时：TimeoutWatchdog 释放。宕机：RecoveryScanner 启动时释放。

DagScheduler.doSchedule()
└→ StepSubmitter.submit()
└→ node.isResourceEnabled() ?
├─ false → 直接 dispatch(ctx) // 开关关闭，跳过资源逻辑
└─ true → ResourcePool.acquire(AcquireRequest)
├→ ResourceSelector.select() // 按类型+区域+健康筛候选设备
├→ 尝试独占资源（本区 EXCLUSIVE）
├→ 尝试共享资源（检验 ZoneQuota）
├─ 失败 → 直接 return，等下轮调度
└─ 成功 → 写 pe_step_resource_hold
→ StepStateMachine.tryStart()
→ dispatch(ctx) // ctx 携带 resourceId

步骤完成（成功 / 失败 / 超时）
└→ releaseIfHeld(executionId, nodeId, attempt, reason)
└→ ResourcePool.release(resourceId, holderKey)
└→ pe_step_resource_hold.released_at = now()

Redis Key 设计

// 资源锁（Hash）
resource:lock:{resourceId} → { holder, zoneCode, acquiredAt }
// 作用：判断设备是否被占用，存储持有者和申请区域

// 持有者反向索引（Set）
resource:holder:{holderKey} → Set<resourceId>
// holderKey = executionId:nodeId:attempt
// 作用：批量释放一个步骤的所有资源（releaseByHolder）

// 区域配额计数（String/Int）
resource:zone:{zone}:borrow:{type} → 当前借用数
// 作用：防止单区垄断 AGV 等共享资源，incrQuota/decrQuota 维护
为什么用 Redis 而不是 DB 做资源锁

资源竞争是毫秒级决策，多个步骤并发争同一台设备，DB 行锁的响应延迟（5-20ms）会成为瓶颈。Redis 的 Hash.putIfAbsent 操作是原子的，延迟在 1ms 以内。DB 表（pe_step_resource_hold）用于审计和宕机恢复，不用于运行时竞争。两者职责完全分开。

完整执行流程（含资源调度）

【流程启动】
POST /pipeline/{key}/start
└→ PipelineExecutionService.start()
├→ [事务内] 创建 pe_pipeline_execution + 初始化所有 pe_step_execution(PENDING)
└→ [事务提交后] DagScheduler.schedule(executionId)

【调度循环】（每轮由节点完成事件触发）
DagScheduler.doSchedule(executionId)
├→ 加载所有步骤状态 → 找就绪节点（PENDING + 依赖全满足）
└→ 并行 forEach(readyNode → StepSubmitter.submit())

【步骤执行】
StepSubmitter.submit(executionId, graph, node)
├→ CONDITION节点：同步执行，不需要资源，直接走
└→ 其他节点：
├→ node.isResourceEnabled() = true → ResourcePool.acquire()
│ ├─ 申请失败 → return（等下轮调度，不改状态）
│ └─ 申请成功 → 写 pe_step_resource_hold → 继续
├→ StepStateMachine.tryStart()（CAS: PENDING→RUNNING）
│ └─ 失败 → rollbackResource() → return
└→ dispatch(ctx) → DispatchSpi 路由执行

【步骤完成回调】
DagScheduler.onStepComplete()
├─ 成功 → StepSuccessHandler → 写上下文 → releaseIfHeld(STEP_COMPLETE) → doSchedule()
└─ 失败 → StepFailureHandler → ExceptionCoordinator
├→ RetryHandler: 重试次数未耗尽 → 延迟重试
├→ CompensationHandler: 需要补偿 → 触发补偿步骤
└→ AlertHandler: 告警 + releaseIfHeld(STEP_DEAD) + FailureImpact 处理

【超时扫描】（每10秒）
TimeoutWatchdog.scan()
└→ 找 RUNNING 且 started_at + timeout_ms < now 的步骤
└→ CAS: RUNNING→TIMEOUT → interrupt线程 → releaseIfHeld(TIMEOUT) → ExceptionCoordinator

【宕机恢复】（启动时扫描）
RecoveryScanner.recover()
└→ 找 RUNNING 状态的步骤
├→ resource_acquired=1 → release(RECOVERY) → 清除 Redis 锁
└→ 重置为 PENDING → 重新参与调度

关键设计决策总结

决策点 选择 为什么不用其他方案
资源锁 Redis Hash + putIfAbsent DB 行锁延迟高（5-20ms），Redis <1ms。资源竞争是高频操作，需要快速响应。
步骤并发控制 DB 乐观锁（tryStart CAS） 分布式锁（Redisson）引入额外依赖和续期问题。乐观锁冲突概率低，冲突时直接放弃不重试，代价小。
上下文存储 Redis 热写 + DB 异步冷备 纯 DB 太慢；纯 Redis 宕机丢数据。双写同步影响主流程性能。热冷分离是最优折中。
超时发现 DB 扫描（每10s） 内存定时器在宕机后丢失，多实例时归属不确定。DB 扫描无状态，任何实例都能接管。
异常处理 独立 ExceptionEngine，责任链 塞进 onStepComplete 会导致主流程膨胀。责任链让策略可配置，新增策略无需改核心代码。
资源等待 直接返回，等下轮调度 阻塞等待会占用线程。独立等待队列增加复杂度。等下轮调度简单，DagScheduler 本来就是重入的。
防死锁 sort_order 全局固定申请序 超时检测+回滚（银行家算法）复杂，还有延迟。固定申请序在定义层解决问题，运行时零开销。
图缓存 ConcurrentHashMap，版本隔离 启动时全量加载浪费内存。懒加载 + 版本 key 保证运行中的执行不受定义修改影响。
