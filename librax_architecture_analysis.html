01

系统全景 · 一句话理解

Librax 是一套 实验室自动化流程编排平台。它的核心使命是：接收一份实验流程定义（DAG 图），按拓扑顺序并行调度执行每个步骤，步骤执行前抢占物理设备资源，执行时通过设备网关下发指令，执行后收集样本检测结果——从「定义一个实验」到「实验自动完成并出报告」的全链路闭环。

核心架构哲学

五模块各司其职，通过 API 层和 Spring Event 解耦：Flow 只管「谁先谁后」，Resource 只管「资源够不够」，Device 只管「怎么跟设备通信」，Task 只管「异步任务排队执行」，Lab 只管「样本状态和结果」。任何模块的内部重构不影响其他模块。

Flow
流程引擎 · 大脑

DAG 调度、状态机、异常处理。决定「下一步做什么」。

Task
任务路由 · 手臂

将步骤转化为具体任务，队列化执行，回调结果。

Device
设备网关 · 手指

多协议驱动，指令下发，状态监控，心跳管理。

Resource
资源调度 · 门卫

设备抢占、区域配额、Redis 锁、防死锁。

Lab
样本管理 · 记录员

样本生命周期、结果采集、溯源追踪。

通过 API 模块（flow-api、device-api）实现反向依赖隔离。实现模块之间不直接依赖，而是通过接口契约通信。这是整个架构中最值得肯定的设计决策之一。

依赖问题发现

task → lab 存在直接依赖，这打破了模块间通过 API 层隔离的设计原则。task 模块应该只依赖 flow-api，不应直接依赖 lab。同样，lab → flow（实现模块）的依赖也不够优雅，应改为依赖 flow-api。详见后文建议。

04

各模块职责详解

A. Flow 模块 — 流程引擎（大脑）

Flow 是整个系统的 中枢调度器。它解决的问题是：给定一个 DAG 流程定义，按拓扑序并行调度执行所有步骤，管理每个步骤和整条流程的状态转换，处理异常/重试/补偿/超时。

核心引擎组件
  • DagScheduler — 拓扑调度，找就绪节点并行提交
  • StepSubmitter — 步骤提交：资源申请 → tryStart → dispatch
  • StepStateMachine — 步骤级乐观锁状态机 (CAS)
  • ExecutionStateMachine — 流程级状态机
  • PipelineGraphBuilder/Cache — DAG 构建与版本缓存
  • ExceptionCoordinator — 责任链异常处理
  • TimeoutWatchdog — 超时扫描 (每10s)
设计亮点
  • 事件驱动：步骤完成触发下一轮调度，无轮询
  • 乐观锁 tryStart：并发安全，冲突时自动放弃
  • Redis + DB 双层上下文：热写冷备
  • 版本隔离图缓存：运行中执行不受定义修改影响
  • SPI 分发：DIRECT / QUEUED 双轨，调度器不感知执行细节
  • 重试即新行：attempt 计数器，完整审计追踪

B. Task 模块 — 任务路由（手臂）

Task 是 Flow 到外部执行系统的 协议适配层。它实现了 DispatchSpi 的 QUEUED 模式，将流程步骤转化为可排队、可路由、可回调的异步任务。支持 AGV、仪器、手动操作、计算等多种任务类型。

核心组件
  • QueuedDispatchSpi — 实现 DispatchSpi，Flow 步骤 → Task 记录
  • TaskRouter — 按任务类型路由到不同队列和并发配置
  • TaskExecutorFactory — 动态注册/获取各类型执行器
  • AgvTaskExecutor — AGV 物流调度
  • InstrumentTaskExecutor — 仪器指令模拟/执行
  • ManualTaskExecutor — 人工操作待办
  • TaskCallbackDispatcher — 统一回调：幂等检查 + CAS 状态更新
设计亮点
  • 非阻塞执行：所有 TaskExecutor 都是 fire-and-forget
  • 统一回调入口：外部系统（AGV、人工审批）统一回调接口
  • 可配置并发：每种任务类型独立队列和并发度
  • 幂等保证：回调时 CAS 防重复处理

C. Device 模块 — 设备网关（手指）

Device 是与 物理设备通信的最后一公里。它封装了多种通信协议（TCP/HTTP/SERIAL/SDK/MOCK），提供统一的「发送指令 → 等待回调」接口，并负责设备心跳监控和健康管理。

核心组件
  • DeviceGateway / DeviceGatewayImpl — 统一设备通信入口
  • DeviceDriver (SPI) — 协议驱动抽象
  • DeviceDriverFactory — 按协议类型路由驱动
  • DeviceSelector — 空闲设备选择 + 负载均衡
  • DeviceStateCache — Redis 双向索引设备状态
  • InstrumentStepExecutor — 实现 StepExecutor，桥接 Flow → Device
  • DeviceQueryApi (SPI) — 对外暴露设备健康查询
设计亮点
  • 多协议抽象：TCP / HTTP / SERIAL / SDK / MOCK 统一 DeviceDriver
  • 命令模板化：参数占位符 ${param}，运行时渲染
  • 双向索引：device→execution 和 execution+node→device 的 O(1) 反查
  • 健康分级：心跳 + 健康等级 + 可用性综合判断
  • 轮询/Webhook 双模式：适配不同设备的异步结果获取

D. Resource 模块 — 资源调度（门卫）

Resource 解决的是 物理设备的独占与共享管理。每个步骤执行前必须抢占到所需设备资源，资源不足时等待下轮调度，不报失败。通过 Redis 锁实现毫秒级竞争，DB 记录审计追踪。

EXCLUSIVE 独占

本区固定设备，同时只能一个步骤使用。Redis Hash putIfAbsent 原子抢占。

SHARED 共享

全局移动设备（如 AGV），跨区调度。Zone Quota 配额防止单区垄断。

三道防线

正常释放 + 超时释放 + 宕机恢复释放。资源永远不会泄漏。

E. Lab 模块 — 样本管理（记录员）

Lab 是面向 实验室业务的领域模块。它管理样本从注册到出结果的完整生命周期，通过 Hook 和 Event Listener 与 Flow 引擎集成，实现「流程驱动样本状态变更」。

核心组件
  • SampleLifecycleService — 样本状态机 (REGISTERED → LOADED → IN_PROCESS → COMPLETED)
  • SampleBindHook — 流程启动前绑定样本到 INSTRUMENT 步骤
  • SampleFlowIntegrationListener — 监听流程事件，驱动样本状态
  • SampleResultHandleService — 解析设备输出为检测结果
  • SampleTraceService — 样本轨迹溯源
  • SampleRelationService — 样本分拆父子关系
集成模式
  • Hook 前置绑定：PipelineStartHook，流程启动前绑样本
  • Event 后置驱动：@EventListener 异步监听流程事件
  • 完全被动：Lab 不主动调度，只响应 Flow 事件
  • 结果解析：步骤成功后自动提取检测数据

06

设计评价 · 亮点与隐患

设计亮点
  • SPI 解耦做得好：flow-api 和 device-api 是真正的接口契约层，不携带实现依赖
  • 乐观锁替代分布式锁：冲突概率低的场景用 CAS，避免了 Redisson 续期、死锁等复杂性
  • Redis + DB 双层：上下文热写冷备、资源锁运行时+审计分离，两个都是正确的折中
  • 资源三道防线：正常/超时/宕机三层释放机制，设计完备
  • Lab 模块完全被动：只通过 Hook 和 Event 响应 Flow，不反向依赖调度逻辑
  • 设备多协议抽象：DeviceDriver SPI 让新协议接入只需一个实现类
  • sort_order 防死锁：定义层解决运行时问题，零开销
潜在风险
  • task → lab 耦合：Task 直接 Maven 依赖 Lab 模块，应通过事件或 lab-api 隔离
  • lab → flow 实现依赖：Lab 依赖 flow 实现而非 flow-api，增加了耦合面
  • 单点 Redis：资源锁和上下文都依赖 Redis，Redis 故障影响全链路
  • 无分布式调度器：DagScheduler 是单进程内的，多实例部署时需要考虑协调
  • 图缓存无淘汰：ConcurrentHashMap 无 TTL/LRU，长期运行可能 OOM
  • 超时扫描依赖 DB：每 10s 全表扫 RUNNING 步骤，数据量大时性能堪忧
  • 缺乏流程级资源预检：每步独立抢占，可能出现流程执行到一半因持续抢不到资源而"饿死"
07

架构改进建议

建议 1：修复模块依赖 — 抽取 lab-api
优先级：高 · 工作量：中

问题：task 直接依赖 lab 实现模块，lab 直接依赖 flow 实现模块。这两处都打破了 API 层隔离原则。


方案：

  • 新建 librax-module-lab-api，将 Lab 对外暴露的接口（如样本查询、样本绑定）提取到此
  • task 改为依赖 lab-api 而非 lab
  • lab 改为依赖 flow-api 而非 flow，通过 Spring Event 接收流程事件（目前已经部分通过 @EventListener 实现）
建议 2：图缓存加淘汰策略
优先级：高 · 工作量：低

问题：PipelineGraphCache 用 ConcurrentHashMap 无 TTL/大小限制，长期运行且流程版本多时会 OOM。


方案：替换为 Caffeine Cache，设置 maximumSize + expireAfterAccess。正在运行的执行会定期访问保持热，结束后自然淘汰。成本极低，收益确定。

建议 3：超时扫描优化 — 索引 + 分片
优先级：中 · 工作量：低

问题：TimeoutWatchdog 每 10s 扫全部 RUNNING 步骤，随着并发执行增多会成为 DB 热点。


方案：

  • pe_step_execution 添加 deadline_at 字段（started_at + timeout_ms 预计算），建联合索引 (status, deadline_at)
  • 扫描改为 WHERE status='RUNNING' AND deadline_at < now()，精确命中超时步骤
  • 多实例部署时按 executionId hash 分片扫描
建议 4：资源预检机制 — 防流程"饿死"
优先级：中 · 工作量：中

问题：当前资源申请是步骤级的，不足则等待。如果一个长流程中某步骤持续抢不到资源，流程会无限等待（"饿死"）。


方案：

  • 流程启动时做一次 资源预检（不抢占，只检查资源是否存在且配置正确）
  • 增加步骤级 resource_wait_timeout：等待超过阈值进入异常处理链
  • 可选：引入资源预留（reservation）机制，启动时批量预留，步骤执行时 confirm
建议 5：Redis 高可用
优先级：中 · 工作量：高

问题：资源锁、设备状态、执行上下文全部依赖 Redis。单点 Redis 故障 = 全链路故障。


方案：

  • 生产环境使用 Redis Sentinel 或 Redis Cluster
  • 资源锁操作增加降级策略：Redis 不可用时临时走 DB 行锁（性能下降但不中断）
  • 上下文 Redis 故障时自动从 DB 恢复（已有 RecoveryScanner 基础）
建议 6：调度器多实例协调
优先级：低（当前单实例足够） · 工作量：高

问题：DagScheduler 是进程内调度，多实例部署时同一个 executionId 可能被多台机器同时调度。虽然 CAS tryStart 保证了安全性，但会产生大量无效竞争。


方案：

  • 短期：executionId 一致性 hash 到固定实例处理（Redis 分片锁）
  • 长期：引入轻量级 leader election（基于 Redis 或 DB），每个 executionId 只有一个 leader 调度
