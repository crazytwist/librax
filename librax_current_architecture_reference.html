Spring Boot 3 · Java 17 DAG Scheduler ResourcePool + Redis Lock SPI + Spring Event
01

架构结论

当前 Librax 的核心不是传统后台管理系统，而是一套实验室自动化流程执行平台。它以 Flow 为编排大脑，以 Resource 约束物理设备和空间，以 Task 承接异步执行队列，以 Device 屏蔽异构仪器通信，以 Lab 保存样本、物料、结果和谱系。

我建议把系统边界固定为一句话：Flow 管流程推进，Resource 管能不能用，Task 管怎么排队执行，Device 管怎么和设备说话，Lab 管业务事实和追溯。 这个边界与当前代码里的 SPI、事件和模块依赖基本一致。

已经落地的能力

DAG 调度、状态机、回调 Token、DIRECT/QUEUED 分发、资源释放唤醒、断点恢复、父子流程资源继承、样本启动钩子、物料核验与扣减事件。

需要持续校准的地方

部分文档仍停留在早期设计；当前实现已经前进。架构参考应以代码中的 API 契约、事件流和数据对象为准。

当前最重要的原则

跨模块只通过 api 模块、SPI 和 Spring Event 交互。业务域和调度域保持弱耦合，避免 Lab、Device、Task 反向侵入 Flow 内部状态机。

我的架构判断

这套架构最有价值的部分是“执行协议层”已经被拆出来了：Flow 不直接知道设备协议，Device 不直接改流程状态，Task 不直接依赖 Flow 实现，Lab 不嵌进调度器。只要这个边界保持住，后续无论接更多设备、更多样本类型，还是将 Task 队列外置，都不会撕裂主架构。

03

主执行链路

01
启动流程
PipelineExecutionServiceImpl.start() 加载流程图、创建 pe_pipeline_execution、初始化 pe_step_execution，执行所有 PipelineStartHook。
02
事务提交后调度
通过 TransactionSynchronization.afterCommit() 发布流程启动事件并调用 DagScheduler.schedule()，避免调度看到未提交数据。
03
DAG 找就绪节点
DagScheduler 读取所有步骤最新状态，筛选 PENDING 且依赖满足的节点，交给 StepSubmitter。
04
提交前置检查
StepSubmitter 生成 callbackToken，解析入参，注入样本参数，调用 MaterialCheckSpi，再调用 ResourcePool.acquire()。
05
分发执行
步骤 CAS 从 PENDING 进入 RUNNING 后，按 dispatchMode 走 DIRECT 或 QUEUED。
06
回调推进
设备、任务、人工或子流程通过 StepCallbackSpi、TaskCompletedEvent 等路径回到 Flow，Flow 更新步骤状态、写上下文、释放资源、触发下一轮调度。
04

Flow 模块

Flow：编排、调度与状态一致性中心
librax-module-flow / librax-module-flow-api

核心职责

  • 管理流程定义、步骤定义、流程实例和步骤实例。
  • 构建并缓存 PipelineGraph，执行 DAG 拓扑调度。
  • 维护 ExecutionStateMachine 与 StepStateMachine。
  • 统一处理同步结果、设备回调、任务事件、子流程回调。
  • 通过事件把流程状态变化广播给 Lab、监控和 WebSocket。

关键实现

  • PipelineExecutionServiceImpl：流程启动事务边界。
  • DagScheduler：查找就绪节点、完成后继续调度。
  • StepSubmitter：入参解析、物料核验、资源申请、分发。
  • DirectDispatchSpi：本地直接执行步骤。
  • StepCallbackService：外部回调统一入口。
  • RecoveryScanner：应用启动后恢复 RUNNING 流程。
模型表/类作用
流程定义pd_pipeline_definition流程 key、版本、默认参数、失败策略、样本模式。
流程步骤pd_pipeline_stepDAG 节点、依赖、分支、资源开关、调度模式、参数映射。
步骤组件pd_step_definition可复用的步骤模板，包括类型、设备类型、命令、Mock 输出。
执行实例pe_pipeline_execution一次运行的主记录，锁定流程版本、父子关系和 subjectId。
步骤执行pe_step_execution每个节点每次 attempt 的运行记录，含 callbackToken、inputSnapshot、状态。
上下文pe_execution_context步骤输出和启动输入的冷备份，Redis 作为热路径。
Flow 模块判断

Flow 的核心设计已经比较成熟：调度器保持“纯拓扑”，副作用放在 StepSubmitter、Success/FailureHandler 和状态机里。后续需要避免把设备选择、物料扣减、样本生命周期这样的业务逻辑写回 Flow 内部。

05

Device 模块

Device：异构设备通信与回调归一层
librax-module-device / librax-module-device-api

核心职责

  • 维护设备实例、协议参数、认证配置和心跳配置。
  • 维护设备指令模板、完成模式、轮询规则和响应解析器。
  • 通过 DeviceDriverFactory 选择 HTTP/TCP/Serial/SDK/Mock 驱动。
  • 处理 WEBHOOK/POLL/SYNC 三种完成路径。
  • 向 Resource 暴露 DeviceQueryApi 供健康筛选。

关键实现

  • DeviceGatewayImpl：设备选择、模板渲染、系统字段注入、驱动发送。
  • DeviceCommandSpiImpl：供 Task 的仪器执行器调用设备。
  • DeviceCallbackHandler：释放设备状态、解析输出、推进 Flow、关闭 Task。
  • CodecExecutor：JSON/REGEX/HEX/SCRIPT 响应解析。
  • HeartbeatWatchdog：设备在线状态维护。
  • DevicePollScheduler：POLL 模式轮询并转为内部回调。
对象关键字段说明
DeviceInfoDOdeviceId / deviceType / protocol / zoneCode / authType / heartbeatCommand一台物理设备的连接和运行时基础配置。
DeviceCommandDOcommandCode / requestTemplate / completionMode / pollPath / codecId设备能力的声明式指令模板。
DeviceCodecDOparseType / fieldMapping / hexRules / regexRules / scriptContent把设备私有响应转为平台 Map 输出。
DeviceStateCacheIDLE / BUSY / OFFLINE / FAULTRedis 中的设备状态和 execution-node 到 device 的反向索引。
Device 模块判断

设备接入的声明式程度已经不错，新增设备主要走 DeviceInfo、DeviceCommand、DeviceCodec 和 DeviceDriver 四件套。代码里需要注意的是设备健康查询当前存在实现细节不一致：DeviceQueryApiImpl.getHealth() 计算了 status 映射，但 builder 中固定返回 HEALTHY，这会影响 Resource 对故障设备的过滤判断。

06

Task 模块

Task：统一执行任务与异步分发层
librax-module-task

核心职责

  • 将 Flow 的步骤分发转换成统一 lab_task 协议。
  • 按任务类型路由到不同执行器：仪器、AGV、人工、计算、通知。
  • 管理任务排队、执行、回调、超时和任务审计。
  • 通过 TaskCompletedEvent 异步通知 Flow 推进 DAG。

关键实现

  • QueuedDispatchSpi：Flow 到 Task 的分发入口。
  • TaskRouter：按 taskType 维护内存队列和并发信号量。
  • TaskExecutorFactory：自动注册任务执行器。
  • InstrumentTaskExecutor：通过 DeviceCommandSpi 发送仪器指令。
  • TaskCallbackDispatcher：任务终态 CAS、释放资源、发布完成事件。
  • TaskTimeoutWatchdog：扫描执行超时、队列等待超时和人工截止时间。
任务类型执行器完成路径
INSTRUMENTInstrumentTaskExecutorSYNC 直接回调；WEBHOOK/POLL 由 DeviceCallbackHandler 推进并关闭任务。
AGVAgvTaskExecutor提交 AGV job，等待外部回调或超时扫描。
MANUALManualTaskExecutor创建人工待办，操作人完成后携带 callbackToken 回调。
COMPUTE / NOTIFY可扩展执行器可走同步完成或外部 Worker 回调。
Task 模块判断

Task 当前是很好的解耦层，但 TaskRouter 仍是进程内队列。它适合单体部署和开发验证；若后续多实例部署或要求任务不丢，建议把队列语义外置到 Redis Stream / MQ，同时保留 lab_task 作为事实表和审计表。

07

Lab 模块

Lab：样本、物料与实验事实域
librax-module-lab

核心职责

  • 维护样本主数据、样本步骤、样本结果、样本事件和样本谱系。
  • 维护物料定义、物料实例、容器类型、物料检查规则和消耗记录。
  • 在流程启动前绑定样本并注入实验参数。
  • 监听 Flow 事件，将流程状态转译成样本生命周期。
  • 通过 Material SPI 在步骤执行前核验库存，步骤成功后异步扣减。

关键实现

  • SampleBindHook：流程启动事务内绑定样本、预绑定步骤、注入参数。
  • SampleContextSpiImpl：步骤入参解析时提供样本实验参数。
  • SampleFlowIntegrationListener：监听 Flow 事件，更新样本状态和结果。
  • MaterialCheckSpiImpl：执行前物料规则核验。
  • MaterialConsumedEventListener：步骤成功后扣减库存并写消耗记录。
  • SampleSplitStepExecutor：样本拆分步骤执行器。
业务对象代表表/类作用
样本主数据lab_sample_info样本状态、实验参数、当前流程、容器与追踪主线。
样本步骤lab_sample_step样本在流程节点上的处理轨迹。
样本结果lab_sample_result从仪器输出落地的检测结果。
样本关系lab_sample_relation拆分、合并、取液等谱系关系。
物料实例lab_material_instance库存、批次、体积/数量、库位和状态。
物料消耗lab_material_consumption步骤维度消耗审计，用于试剂批次追溯。
Lab 模块判断

Lab 模块最适合承载实验室业务事实，而不是控制调度。当前通过 Hook、SPI、Event 和 Flow 解耦的方式是正确方向。需要特别注意物料扣减监听器目前异步执行，若业务要求“扣减失败必须回滚步骤成功”，就需要把扣减从异步事件升级为同步事务或补偿事务。

Resource 模块

Resource：物理资源锁、区域配额与空间模型
librax-module-resource

核心职责

  • 维护可调度资源、独占/共享属性和区域配额。
  • 维护货架、台面、槽位和物理坐标。
  • 通过 Redis 锁保证同一资源不会被并发超卖。
  • 写入 pe_step_resource_hold 占用记录用于审计和恢复。
  • 资源释放时发布事件，唤醒等待该资源的流程。

关键实现

  • ResourcePoolImpl：资源申请、释放、继承和事件发布。
  • ResourceSelector：按配置和设备健康筛选候选资源。
  • RedisResourceLock：资源锁、holder 反向索引和共享资源配额计数。
  • ResourceReleaseWakeupListener：释放事件唤醒等待执行。
  • ResourceWaitRegistry：Redis Set 记录等待资源的 executionId。
  • SlotCoordinateSpi：为 AGV/机械臂解析库位坐标。
模型说明当前状态
lab_resource_config资源 ID、资源类型、独占/共享、所属区域、最大并发、启用状态。已接入运行时
lab_zone_quota共享资源在区域维度的最大借用量。已接入运行时
pe_step_resource_hold步骤占用资源记录，支持 ACQUIRED / INHERITED。已接入运行时
pd_step_resource_req步骤多资源需求定义。有模型与管理接口，主调度仍以单资源为主
lab_rack_info / lab_slot_info实验室空间、槽位、坐标和容量。已建模，可供 AGV/物料位置扩展
Resource 模块判断

Resource 已经从“配置表”升级为“运行时调度门卫”。当前强项是锁、配额、释放唤醒和父子流程继承。下一步最有价值的是把 pd_step_resource_req 的一步多资源定义完整接入 StepSubmitter，形成全量的批量申请与回滚协议。

我建议的演进方向

P0：修正设备健康视图

DeviceQueryApiImpl.getHealth() 应返回计算出的 healthStatus，否则 Resource 可能把离线/故障设备视为健康候选。

P0：统一资源 ID 到设备下发

StepSubmitter 已把 _resourceId 注入 inputParams。Device/Task 路径应优先使用该 resourceId 指定设备，避免资源锁和实际设备选择不一致。

P1：普通步骤一步多资源

将 pd_step_resource_req 接入 StepSubmitter，按 sortOrder 批量申请，任意失败则释放已申请资源并注册等待。

P1：任务队列外置

保留 lab_task 事实表，将 TaskRouter 的内存队列替换为 Redis Stream 或 MQ，以支持多实例和重启恢复。

P1：物料扣减一致性策略

如果实验合规要求强一致，物料扣减不应只依赖异步事件；可改为同步扣减，或引入失败补偿和待人工处理状态。

P2：统一运行观测模型

围绕 executionId / nodeId / attempt / taskId / callbackToken / resourceId 建立链路视图，串起 Flow、Task、Device、Resource、Lab。
