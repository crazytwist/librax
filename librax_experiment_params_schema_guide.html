01

设计结论

Librax 的参数管理不应该以“设备最终报文”为中心，而应该以 Experiment Params Schema 为统一参数源。流程、步骤、样本、载具、设备、运行时计算结果都按作用域进入同一个结构，最终设备 payload 只是运行时渲染产物。
参数源分层

区分全局参数、载具参数、步骤参数、样本参数、设备模板和运行时参数，避免所有字段平铺到一个上下文里。

按 stepKey 生效

样本参数和步骤参数都按 stepKey 组织。流程运行到某个节点时，只提取这个节点需要的参数片段。

设备报文运行时组装

后处理机台、AGV 等最终 payload 由 Compute 节点和设备命令模板组装，不建议用户直接维护大 JSON。

02

当前问题

问题表现风险建议
参数平铺 样本参数、步骤参数、设备参数、运行时参数容易混在一起。 字段来源不清，后续流程一多会难以维护。 引入 experimentParams.v1，明确作用域。
设备报文和配置耦合 用户容易直接配置 tasks/sampleInfos/stations 这种最终设备结构。 设备协议一变，样本和流程配置都被牵动。 设备模块维护命令模板，Compute 节点负责组装。
样本参数无 step 归属 样本表里有很多字段，但不是每个步骤都会使用。 节点执行时可能拿到不属于自己的字段。 样本参数使用 common + stepParams。
深层路径解析不足 表达式如 ${experiment.stepParams.postProcessor.stations} 需要稳定支持。 复杂参数只能靠 Compute 手工取值。 增强表达式解析器，支持嵌套 path。
03

核心原则

定义参数
用 Schema 定义字段归属、类型、必填、默认值和生效 stepKey。
绑定流程
流程只声明本次实验需要哪些参数包、载具、样本和步骤。
节点取参
节点根据 stepKey 从全局上下文中取自己的参数片段。
运行时计算
库位、载具位置、AGV 指令等由 Compute 节点计算。
模板渲染
设备命令模板引用系统参数、步骤参数和运行时结果。
设备下发
Device 节点只负责执行命令和处理回调，不再理解业务参数来源。
推荐规则：配置阶段维护“参数定义”和“参数来源”，运行阶段产生“设备报文”。不要把最终设备 JSON 反向当成参数管理的主模型。
04

Experiment Params Schema 标准

建议统一使用 experimentParams.v1 作为流程启动、样本绑定、节点取参和设备组装的公共结构。

recommended skeleton
{
  "schemaVersion": "experimentParams.v1",
  "globalParams": {},
  "carrierParams": {},
  "stepParams": {},
  "sampleParams": {},
  "deviceParams": {},
  "runtimeParams": {}
}
分区归属示例字段维护位置使用者
globalParams 流程级公共参数 experimentNo、batchNo、zoneCode、operator 流程启动入参或流程定义默认值 所有节点
carrierParams 载具、托盘、盘号、库位 carrierNo、carrierType、currentLocation、targetLocation 启动入参、物料/库位查询结果 AGV、后处理机台、上下料节点
stepParams 步骤级工艺参数 postProcessor.stations、agvMove.taskType 步骤定义默认值 + 流程节点覆盖值 对应 stepKey 的节点
sampleParams 样本公共参数和样本步骤参数 samples[].common、samples[].stepParams.postProcessor 样本表 experiment_params 或样本参数配置模块 样本绑定节点、设备 payload builder
deviceParams 设备命令、协议、模板引用 POST_PROCESSOR.startTask、AGV.startTask Device 模块或参数模板表 设备网关、设备节点
runtimeParams 流程执行中产生的结果 carrierLocation、agvCommand、postProcessorPayload Execution Context / 节点输出 后续节点
05

和现有 Librax 底座的映射

现有能力建议承载内容说明
pd_pipeline_definition.default_input_params schemaVersion、globalParams 默认结构 定义流程级默认参数，不放具体设备最终报文。
pd_step_definition.default_params 某类步骤的默认 stepParams 比如后处理步骤默认站点参数、AGV 步骤默认任务类型。
pd_pipeline_step.params_override 某个流程节点对默认步骤参数的覆盖 同一个 StepDefine 在不同流程里可以配置不同目标点位、不同工艺默认值。
pd_pipeline_step.input_mapping 节点入参和上下文路径的映射关系 声明节点从 experiment、runtime、sys 中取什么。
lab_sample_info.experiment_params sampleParams.samples[].common 和 sampleParams.samples[].stepParams 样本表只维护样本自身参数，不直接维护设备下发 JSON。
Execution Context / Node Output runtimeParams 库位查询、载具绑定、AGV 指令、机台 payload 等运行时结果进入这里。
现阶段可以先通过规范约束这些表的 JSON 结构；后续再补 Schema 校验、深层 path 解析和参数预览能力。
06

样本参数标准

样本参数不要直接保存设备最终需要的 sampleInfos，而是保存样本公共参数和按步骤生效的参数。

sample experiment_params example
{
  "schemaVersion": "sampleParams.v1",
  "common": {
    "sampleId": "SAMPLE-001",
    "sampleNo": "SAMPLE-001",
    "carrierNo": "PP-4-1",
    "hole": 1
  },
  "stepParams": {
    "postProcessor": {
      "filterTimeSec": 10,
      "nitrogenBlowingStepCount": 2,
      "liquidSteps": [
        {
          "index": 1,
          "stepType": "quench",
          "solventCode": "1",
          "volumeUl": 1000
        },
        {
          "index": 2,
          "stepType": "wash",
          "solventCode": "1",
          "volumeUl": 1000
        },
        {
          "index": 3,
          "stepType": "recovery",
          "solventCode": "1",
          "volumeUl": 1000
        }
      ]
    }
  }
}
字段归属说明
common.sampleId、common.hole 样本公共参数 任何需要识别样本和孔位的节点都可以使用。
stepParams.postProcessor.filterTimeSec 样本步骤参数 只在后处理步骤组装机台 payload 时使用。
stepParams.postProcessor.liquidSteps 样本步骤参数 用于生成设备报文中的 sampleInfos[].steps。
07

步骤参数标准

步骤参数描述“这个节点怎么运行”，不是“这个设备最终收到什么”。同一个步骤的默认参数放在 StepDefine，某条流程的差异放在 PipelineStep override。

stepParams example
{
  "stepParams": {
    "postProcessor": {
      "stations": [
        {
          "stationCode": "quench",
          "tempC": 20,
          "timeSec": 20,
          "rpm": 300,
          "flowAir": 0,
          "steps": []
        },
        {
          "stationCode": "nitrogenBlowing",
          "tempC": 20,
          "timeSec": 0,
          "rpm": 0,
          "flowAir": 30,
          "steps": [
            {
              "index": 1,
              "blowAir": false,
              "moveLengthMm": 45,
              "moveTimeSec": 5,
              "waitTimeSec": 0
            }
          ]
        }
      ]
    },
    "agvMoveToPostProcessor": {
      "taskType": "1",
      "plateType": "Plate_5",
      "targetStation": "AP5",
      "targetArea": "POST_PROCESSOR",
      "targetPos": "1"
    }
  }
}
建议所有步骤都拥有稳定的 stepKey。样本参数、步骤参数、设备模板和 Compute 节点都用这个 stepKey 对齐。
08

设备命令模板

设备模块应该维护接口协议和命令模板。模板引用上下文路径，不直接包含业务计算逻辑。

后处理机台 startTask 模板
{
  "deviceType": "POST_PROCESSOR",
  "commandCode": "startTask",
  "schemaVersion": "postProcessor.startTask.v1",
  "payloadTemplate": {
    "callbackToken": "${sys.callbackToken}",
    "callbackUrl": "${sys.callbackUrl}",
    "executionId": "${sys.executionId}",
    "nodeId": "${sys.nodeId}",
    "tasks": "${runtime.postProcessor.tasks}"
  }
}
AGV startTask 模板
{
  "deviceType": "AGV",
  "commandCode": "startTask",
  "schemaVersion": "agv.startTask.v1",
  "payloadTemplate": {
    "taskId": "${runtime.agv.taskId}",
    "agvCmdList": "${runtime.agv.agvCmdList}"
  }
}
设备模板的职责是“把已经准备好的上下文字段渲染成接口报文”。比如 AGV 的 sourceArea、sourcePos 应该在调用 AGV 前由库位查询和命令构建节点准备好。
09

运行时组装模型

Compute 节点负责把结构化参数转换成设备可识别的运行时 payload。推荐每个复杂设备都有专门的 Payload Builder。

Compute 节点输入输出说明
carrierSampleQuery carrierNo runtime.carrierSamples 查询载具下的样本和孔位。
carrierLocationQuery carrierNo runtime.carrierLocation 查询载具当前库位，用于 AGV source 参数。
agvCommandBuilder carrierLocation、stepParams.agv* runtime.agv.agvCmdList 生成 AGV startTask 报文主体。
processorTaskPayloadBuilder carrier、samples、stepParams.postProcessor runtime.postProcessor.tasks 生成后处理机台 tasks 内容。

后处理机台示例

后处理机台最终 payload 中的 sampleInfos 来自样本步骤参数，stations 来自步骤参数，trayInfo 来自载具/库位运行时结果。

runtime assembled payload
{
  "callbackToken": "690f83dfde754e0698b5f565ca1d989c",
  "callbackUrl": "http://localhost:48080/app-api/device/callback/...",
  "executionId": "8bbc817bd4ad42deb0ff6bacfbfb59d8",
  "nodeId": "s_start_post_processor",
  "tasks": [
    {
      "trayInfo": {
        "typeCode": "1",
        "address": "13",
        "needRetain": true
      },
      "stations": "${experiment.stepParams.postProcessor.stations}",
      "sampleInfos": [
        {
          "sampleId": "SAMPLE-001",
          "hole": 1,
          "filterTimeSec": 10,
          "nitrogenBlowingStepCount": 2,
          "steps": "${sample.stepParams.postProcessor.liquidSteps}"
        }
      ]
    }
  ]
}
最终字段来源说明
tasks[].trayInfo runtime.carrierLocation + carrierParams 载具类型、当前位置、是否保留固体等。
tasks[].stations stepParams.postProcessor.stations 机台站点公共工艺参数。
tasks[].sampleInfos sampleParams.samples[].common + stepParams.postProcessor 每个样本的孔位、过滤时间、液体步骤等。

12

参数管理页面建议

页面不要让用户直接编辑最终 payload，而是分层管理参数，并提供最终报文预览。

参数模板库
  • 维护 experimentParams.v1 标准字段。
  • 字段类型、单位、默认值、必填、说明。
  • 字段归属：全局、载具、步骤、样本、设备、运行时。
流程参数配置
  • 配置流程级 globalParams。
  • 选择载具、样本、步骤参数包。
  • 绑定每个节点的 stepKey。
样本参数矩阵
  • 按样本、孔位、步骤维护参数。
  • 支持批量编辑液体步骤、体积、过滤时间。
  • 只展示当前流程会消费的字段。
参数预览和校验
  • 预览每个节点最终入参。
  • 预览设备最终下发 payload。
  • 提示缺失字段、未消费字段、类型错误。

14

落地路线

第一阶段：先统一规则

  • 把 experimentParams.v1 作为新流程默认参数结构。
  • 后处理流程和 AGV 流程先按新结构配置。
  • 样本参数先约定 common + stepParams，不再继续新增平铺字段。

第二阶段：增强底座能力

  • 增强表达式解析，支持嵌套 path。
  • 调整样本参数注入方式，避免无作用域平铺合并。
  • 把后处理和 AGV payload builder 接入统一 Schema。

第三阶段：做参数管理模块

  • 建设参数模板库、设备命令模板、样本参数矩阵。
  • 增加参数预览、校验、字段来源追踪。
  • 让业务配置人员能看到“这个字段来自哪里、流向哪里、最终长什么样”。
最终目标：所有流程参数都从统一上下文中获取；所有设备报文都从模板和运行时上下文中生成；所有样本差异都按 stepKey 管理。
