1三层架构概览

整个设计分三层，每一层职责明确，下层可覆盖上层的默认值：

Layer 1 — 步骤定义 pd_step_definition（可复用模板）

描述"一种步骤能做什么"：设备类型、执行器、默认参数、超时、重试策略等。一次定义，多个流程复用。

↕ 绑定 + 选择性覆盖
Layer 2 — 流程定义 pd_pipeline_definition（全局配置）

描述"一条流程的整体策略"：失败策略、补偿策略、全局默认超时/重试。不涉及具体步骤。

↕ 绑定 + 节点编排
Layer 3 — 步骤绑定 pd_pipeline_step（关联 + 覆盖 + 编排）

将步骤定义"装入"流程，定义节点 ID、DAG 依赖关系、参数覆盖、输入/输出映射、资源配置。这是前端"流程编辑器"操作的核心表。


数据流向：

+
pd_pipeline_step

→ 合并 →

前端页面边界 步骤定义页面：维护"步骤模板库"，改一次全局生效。
流程定义页面：配置流程基本信息和全局策略。
流程编辑器（画布）：操作 pd_pipeline_step，绑定步骤、连线、覆盖参数。
执行监控页面：查看 pe_step_execution，只读。

2步骤定义（pd_step_definition）— 步骤模板库

步骤定义是可复用的"步骤模板"，与具体流程无关。改这里会影响所有引用该步骤的流程（除非绑定时指定了具体版本）。

身份字段（创建后不可改）

字段说明示例
step_key步骤唯一标识，小写下划线命名，全局唯一ph_measure
version版本号（从 1 开始递增），(stepKey, version) 联合唯一1
name显示名称PH检测
description步骤说明
statusACTIVE DISABLED

步骤类型（决定执行器路由）

step_type含义需要配置的字段
INSTRUMENT调用物理设备device_type + command
COMPUTE调用 Spring Bean 或 LiteFlow 链executor + bean_name/chain_id
CONDITION条件分支节点（在绑定层配 conditionExpr）无特殊字段，分支配置在 pd_pipeline_step
WAIT等待外部事件/定时default_timeout_ms
UNIT_LAUNCHER为每个样本启动子流程default_params（指定子 pipelineKey）
MANUAL需人工确认才继续无特殊字段
NOTIFY通知节点bean_name（通知实现类）
SAMPLE_SPLIT样本拆分default_params（拆分规则）

设备执行字段（INSTRUMENT 类型专用）

字段说明是否可被绑定层覆盖
device_type设备类型，如 PH_METER、AGV不可覆盖（由步骤决定）
command默认设备指令，如 MEASURE不可覆盖

计算执行字段（COMPUTE 类型专用）

字段说明
executorBEAN = 调 Spring Bean；LITEFLOW = 走 LiteFlow 规则链
bean_nameSpring Bean 名称（executor=BEAN 时必填）
method_nameBean 方法名
chain_idLiteFlow 链 ID（executor=LITEFLOW 时必填）

可在绑定层覆盖的默认值

以下字段是"步骤级默认值"，可在 pd_pipeline_step 中针对某个流程节点单独覆盖：

字段说明默认值
default_params默认参数（JSON），绑定层用 params_override 做增量覆盖{}
params_schema参数表单 schema（JSON Schema），供前端渲染动态表单null
output_fields输出字段声明（JSON 数组），如 ["ph","temperature"]，供后续节点 inputMapping 引用null
default_timeout_ms默认超时毫秒数null（继续往上找）
default_max_attempts默认最大重试次数null
default_backoff_ms默认重试退避间隔（ms）null
compensate_step_key默认补偿步骤 keynull
compensate_params补偿步骤默认参数（JSON）null
runnable_standalone是否可独立运行/测试true
mock_output独立测试时的模拟输出（JSON）null
output_fields 是连接上下游的关键 声明 output_fields: ["ph", "temperature"] 后，下游节点可在 inputMapping 中写 "${s_ph.ph}" 引用这个值。前端编辑器可据此做自动补全提示。

3流程定义（pd_pipeline_definition）— 全局配置

流程定义描述整条流程的"全局策略"，不涉及具体步骤节点，但它的默认值会作为兜底供节点继承。

身份字段

字段说明示例
pipeline_key流程唯一标识，小写下划线water_quality_test
version版本号，(pipelineKey, version) 联合唯一1
name显示名称水质检测流程
description流程说明
statusDRAFT ACTIVE DISABLED只有 ACTIVE 状态才能被启动
published_at发布时间（status 变为 ACTIVE 时记录）

全局策略字段（作为节点兜底值）

字段取值说明
fail_strategyFAIL_FAST CONTINUE_ON_FAIL任意节点失败时的全局策略：FAIL_FAST=整条流程终止；CONTINUE_ON_FAIL=跳过失败节点继续
compensate_strategyNONE ON_FAIL ALWAYS全局补偿触发时机
default_timeout_ms整数（ms）节点没配 timeout 时的兜底值
default_max_attempts整数节点没配 maxAttempts 时的兜底值
default_backoff_ms整数（ms）节点没配 backoffMs 时的兜底值

样本绑定字段

字段说明
sample_mode样本绑定模式，当前固定为 REQUIRED
sample_bind_nodes触发样本绑定的节点 ID 列表（JSON 数组）
流程定义与步骤定义的关系 流程定义本身不包含任何步骤信息。步骤是通过 pd_pipeline_step 关联进来的。 前端"流程定义"页面只需管理上面这些字段，步骤的编排在画布/编辑器里完成。

4步骤绑定（pd_pipeline_step）— 关联与覆盖

这是最核心的关联表，一行 = 流程中的一个节点。它同时承担三个职责：①把步骤定义"装入"流程；②定义 DAG 拓扑（前后依赖）；③按需覆盖步骤定义的默认值。

4.1 创建关联时必须传递的字段（最小必填集）

在流程编辑器中绑定步骤时，以下字段必须明确配置
字段说明示例
pipeline_key所属流程的 keywater_quality_test
pipeline_version所属流程的版本号1
node_id节点在此流程中的唯一 ID，小写下划线，建议以 s_ 开头s_ph
step_key引用的步骤定义 keyph_measure
depends_on前置节点 ID 列表（JSON 数组或逗号分隔），入口节点填 [] 或 null["s_sample_in"]

字段说明何时配置

5字段归属与覆盖优先级

5.1 覆盖优先级（Coalesce 链）

执行引擎在构建 StepNode 时，对每个参数依次查找，取第一个非 null 值：

pd_pipeline_step
节点级覆盖
最高优先级
→
pd_step_definition
步骤级默认值
→
pd_pipeline_definition
流程级全局默认
→
系统硬编码
最终兜底
如 backoff=2000ms
// PipelineGraphBuilder.assembleNode() 核心逻辑（伪代码）
timeoutMs    = coalesce(ps.timeoutMs,   sd.defaultTimeoutMs,   pd.defaultTimeoutMs,  null)
maxAttempts  = coalesce(ps.maxAttempts, sd.defaultMaxAttempts, pd.defaultMaxAttempts, 1)
backoffMs    = coalesce(ps.backoffMs,   sd.defaultBackoffMs,   pd.defaultBackoffMs,   2000)
onFailure    = coalesce(ps.onFailure,   pd.failStrategy)
stepType     = coalesce(ps.stepType,    sd.stepType)            // 非空优先

// 参数合并：base + delta
params = merge(sd.defaultParams, ps.paramsOverride)             // paramsOverride 只需填要改的 key

// 布尔字段：绑定层 > 步骤层 > true（默认可运行）
runnableStandalone = coalesce(ps.runnableStandalone, sd.runnableStandalone, true)

6执行层（pe_step_execution）

执行层是只追加、不修改的快照记录，每次重试创建新行，完整保留历史。

身份字段

字段说明
execution_id所属流程执行 ID
node_id对应 pd_pipeline_step.node_id
step_key冗余存储，便于统计
attempt第几次尝试（从 1 开始），重试不覆盖旧记录

状态字段

status含义
PENDING等待依赖完成
RUNNING执行中
SUCCESS成功
FAILED失败
SKIPPED被跳过
DEAD超出最大重试
COMPENSATING补偿执行中
COMPENSATED补偿完成

7完整操作流程：从编写步骤到串起流程

Step 1：定义步骤（步骤模板库）

进入步骤定义管理，新增步骤模板。关键决策：

  1. 确定 step_key（全局唯一，建议 动词_名词 格式，如 measure_ph）
  2. 选择 step_type（INSTRUMENT / COMPUTE / CONDITION 等）
  3. 填写类型专属字段（INSTRUMENT 填 device_type+command，COMPUTE 填 executor+bean_name）
  4. 声明 output_fields（后续步骤 inputMapping 引用的字段名）
  5. 填写 default_params（步骤参数的默认值 JSON）
  6. 可选：填写 params_schema（供前端渲染动态表单）
  7. 设置合理的 default_timeout_ms、default_max_attempts
步骤定义好后 status 设为 ACTIVE，才能被流程引用。

Step 2：定义流程基本信息

进入流程定义管理，新增流程。关键决策：

  1. 确定 pipeline_key（全局唯一）
  2. 选择 fail_strategy：实验流程通常用 FAIL_FAST（缺料/设备故障立即停止）
  3. 设置全局默认 timeout / maxAttempts（作为兜底，节点没配时使用）
  4. 此时 status 保持 DRAFT，待所有节点配好后再发布

Step 3：在流程中绑定步骤（画布编辑器）

进入流程编辑器，每添加一个节点都会创建一条 pd_pipeline_step 记录：

  1. 选择步骤：从步骤模板库中选 step_key，分配唯一 node_id（如 s_ph）
  2. 连线：拖动建立依赖，对应填写 depends_on（入口节点留空）
  3. 配置 inputMapping：引用上游节点输出，如 {"sampleId":"${input.sampleId}"}
  4. 配置 outputMapping：将设备回调字段映射到上下文 key
  5. 按需覆盖：只改和步骤默认值不同的参数（paramsOverride、timeout 等）
  6. 配置资源：INSTRUMENT 节点开启 resource_enabled，填 zone_code
  7. CONDITION 节点：填 condition_expr、true_branch、false_branch

Step 4：发布流程

所有节点配置完成后，将流程 status 改为 ACTIVE，记录 published_at。

发布后修改 ACTIVE 流程建议创建新版本（version+1）而非直接修改，避免影响正在执行的实例。 正在执行的实例绑定的是启动时的版本，不受新版本影响。

Step 5：启动流程

调用 POST /flow/pipeline-execution/start，传入：

{
  "pipelineKey":    "water_quality_test",
  "pipelineVersion": 1,              // null 则自动用最新 ACTIVE 版本
  "inputParams": {
    "sampleId": "S-20260611-001"  // 步骤通过 ${input.sampleId} 引用
  },
  "triggerType":     "MANUAL",
  "triggeredBy":     "admin"
}

Step 6：执行监控

查询 pe_step_execution 实时跟踪每个节点状态，支持：

  • 查看 input_snapshot（该节点实际收到的参数）
  • 查看 output_data（该节点的输出，可被下游引用）
  • 查看 wait_ms / execute_ms（排队/执行耗时分析）
  • 重试历史（同一 node_id 的多条 attempt 记录）

8典型配置示例

示例 1：pH 检测步骤绑定

步骤定义中已有默认超时 30s，此节点需要 60s，且要引用上游采样步骤的 sampleId：

// pd_pipeline_step 核心字段
{
  "pipelineKey":    "water_quality_test",
  "pipelineVersion": 1,
  "nodeId":          "s_ph",
  "stepKey":         "measure_ph",
  "dependsOn":       ["s_sample_in"],
  "inputMapping":    { "sampleId": "${input.sampleId}" },
  "outputMapping":   { "ph": "$.result.phValue" },
  "timeoutMs":       60000,       // 覆盖步骤默认 30000
  "paramsOverride":  { "channel": "2" },  // 只改 channel，其他参数用步骤默认值
  "resourceEnabled": true,
  "zoneCode":        "ZONE-A"
}

示例 2：条件分支节点

pH 合格（6.5~8.5）走归档，否则走复测：

{
  "nodeId":        "s_ph_check",
  "stepKey":       "condition_check",
  "stepType":      "CONDITION",        // 覆盖步骤定义的默认类型（此处就是 CONDITION）
  "dependsOn":     ["s_ph"],
  "conditionExpr": "${s_ph.ph} >= 6.5 && ${s_ph.ph} <= 8.5",
  "trueBranch":    "s_archive",
  "falseBranch":   "s_retest"
}

示例 3：参数合并逻辑

// pd_step_definition.default_params
{ "channel": "1", "unit": "pH", "calibrate": true, "retryOnError": false }

// pd_pipeline_step.params_override（只填要改的）
{ "channel": "2", "retryOnError": true }

// → 合并后 StepNode.params（执行时实际使用）
{ "channel": "2", "unit": "pH", "calibrate": true, "retryOnError": true }

示例 4：input/output 上下文传递

// s_sample_in（采样步骤）output_mapping
{ "sampleVolume": "$.result.volumeUl" }
// → 写入上下文 key: "s_sample_in.sampleVolume"

// s_dilute（稀释步骤）input_mapping
{ "inputVolume": "${s_sample_in.sampleVolume}" }
// → 执行时将上下文中 s_sample_in.sampleVolume 的值注入 inputVolume 参数

// 流程启动时的 inputParams 也可以引用
